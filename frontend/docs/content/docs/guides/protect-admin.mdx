# Protect the admin dashboard

Octopus ships a built-in [admin dashboard](/docs/observability/admin-dashboard):
a web UI plus a JSON REST API for routes, health, metrics, plugins, config, and
FARP services. It is served on the gateway's listen port (or on the private
`admin.listen` port when you set one) and, out of the box, **requires no
authentication**. Anyone who can reach the port can read your gateway's
internals.

You have two ways to close it. The quick one is a password or API token in the
environment, covered first. The other puts it behind one of your auth providers,
which the steps further down walk through.

<Callout type="info">
  Whichever you pick, combine it with `admin.allowed_ips` (an IP / CIDR / range
  allowlist that returns `403` to non-matching clients) and network-layer
  controls (NetworkPolicy, firewall). See
  [Admin configuration](/docs/configuration/admin).
</Callout>

## Quick option: a password or API token

Set a secret and start the gateway:

```bash
export OCTOPUS_ADMIN_PASSWORD=change-me          # people: sign-in form and session cookie
export OCTOPUS_ADMIN_API_TOKEN=a-long-random-one  # machines: token on every request
octopus serve -c gateway.yaml
```

Either one is enough. The log line `Admin authentication enabled: password login, API token`
tells you which are on. From then on `/admin/api/*`, `/admin/ws` and the
server-rendered pages under `/admin` answer `401` without credentials. A machine
client sends the token as `Authorization: Bearer <token>` or as
`X-Octopus-Admin-Token: <token>`:

```bash
# Unauthenticated -> 401 {"error": "Authentication required"}
curl -i http://localhost:8080/admin/api/routes

# Either header form works
curl -i -H "X-Octopus-Admin-Token: $OCTOPUS_ADMIN_API_TOKEN" http://localhost:8080/admin/api/routes
```

Open `/admin` in a browser and, with a password set, the `401` page is a
sign-in form. Enter `OCTOPUS_ADMIN_USERNAME` (default `admin`) and the password;
the form posts them to `/admin/api/auth/login`, the gateway sets the session
cookie, and the page reloads signed in. The published image serves only these
server-rendered pages, not the `/admin/ui` SPA, so this form is the way in.
With only `OCTOPUS_ADMIN_API_TOKEN` set the `401` page has no form, since
there is no password to sign in with.

If you reach the gateway through the Kubernetes API service proxy, use
`X-Octopus-Admin-Token`. The kube-apiserver strips `Authorization` once it has
authenticated you, so the bearer form never arrives.

To make sure a forgotten secret can't leave the dashboard open, add
`require_auth`. The gateway then refuses to start without credentials:

```yaml title="gateway.yaml"
admin:
  require_auth: true
```

## Using an auth provider

<Steps>

<Step>
### Define an auth provider for the dashboard

Any [auth provider](/docs/configuration/auth) works. A dedicated JWT provider for
operators is a common choice; you could equally reuse an existing provider or use
[API key](/docs/security/api-key), [mTLS](/docs/security/mtls), or
[forward auth](/docs/security/forward-auth).

```yaml title="gateway.yaml"
auth_providers:
  dashboard-auth:
    type: jwt
    secret: "${ADMIN_JWT_SECRET}"
    algorithm: HS256
    issuer: https://auth.example.com
```
</Step>

<Step>
### Point the admin block at it

Set `admin.auth_provider` to the **name** of that provider. Every `/admin*`
request is then run through it before the dashboard is dispatched;
unauthenticated requests get `401 Unauthorized`. If you also set
`OCTOPUS_ADMIN_PASSWORD` or `OCTOPUS_ADMIN_API_TOKEN`, a request has to pass both.

```yaml title="gateway.yaml"
admin:
  auth_provider: dashboard-auth   # must match an auth_providers key
```

<Callout type="info">
  Static assets are exempt: requests whose path contains `/static/` or `/_next/`
  bypass the admin auth check so login-protected pages can still load their CSS
  and JS. This is wired in the runtime.
</Callout>
</Step>

<Step>
### Validate and run

```bash
export ADMIN_JWT_SECRET=change-me
octopus validate -c gateway.yaml
octopus serve -c gateway.yaml
```

The full configuration (a real upstream is included so the gateway also proxies
traffic; the admin protection works the same with or without it):

```yaml title="gateway.yaml"
gateway:
  listen: "0.0.0.0:8080"

upstreams:
  - name: app
    instances:
      - id: app-1
        host: 10.0.0.51
        port: 8080

auth_providers:
  dashboard-auth:
    type: jwt
    secret: "${ADMIN_JWT_SECRET}"
    algorithm: HS256
    issuer: https://auth.example.com

admin:
  auth_provider: dashboard-auth

routes:
  - path: /*
    upstream: app
```
</Step>

<Step>
### Verify it is protected

```bash
# Unauthenticated -> 401
curl -i http://localhost:8080/admin

# With a valid token from dashboard-auth
curl -i -H "Authorization: Bearer $ADMIN_TOKEN" http://localhost:8080/admin
```

The same protection covers the JSON API under `/admin/api/*` and the `/__admin`
alias. The dashboard's pages and endpoints are documented in
[Admin dashboard](/docs/observability/admin-dashboard) and the
[Admin API](/docs/observability/admin-api) reference.
</Step>

</Steps>
